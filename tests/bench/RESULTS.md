# 基准测试结果：单进程基线与多进程容量

简体中文 | [English](./RESULTS_EN.md)

对 media-server 做的端到端性能基准测试。

> **对比注意**：不同机器、不同推流方式、不同测量口径的数值**不可直接比较**。
> 本数据只用于「select vs event」「改造前 vs 改造后」的自身对比。
>
> 本文下半部分是**旧单进程架构的历史基线**（select vs event、单进程容量），
> 上半部分是**当前多进程架构的容量测试**（2026-11-27）。两者口径不同，
> 但每单位成本可直接对照。

## 多进程容量测试（当前，`capacity_*` 结果文件）

**测试策略**：服务端（control / ingest / play / admin）只启动一次、全程不重启；
每 5s 给每个未饱和的 play/ingest 进程追加 100 路；单进程 CPU 连续 ≥80% 维持 30s
才锁定该进程（回落则解锁继续加）；全部锁定后保持 40s 做稳定性考核。

**测试条件**：AMD Ryzen 9 9900X（12C/24T）、Windows、PHP 8.4.25、
1080p30 4096 kb/s、ffmpeg `-c copy` 推流、rtmpstress 拉流、录像关闭。

### 拉流容量 vs play 进程数

| play 进程 | 容量（路） | 稳态平均 CPU/进程 | 内存(ws) | 每进程容量 | 结果文件 |
|---|---|---|---|---|---|
| 1 | 950 | 98.9% | 102 MB | 950 | `capacity_pull_..._155401.json` |
| 2 | 1600 | 94.8% | 69 MB | 800 | `..._162152.json` |
| 5 | 3000 | 98.4% | 160 MB | 600 | `..._164328.json` |
| 6 | **3599** | 103.2% | 196 MB | 600 | `..._164609.json` |
| 6 + JIT | 3600 | 97.2% | 245 MB | 600 | `..._165532.json` |
| 6 + 关GC | 3600 | 103.8% | 188 MB | 600 | `..._170035.json` |
| 8 | 3200 | 100.2% | 231 MB | 400 | `..._164812.json` |
| 10 | 4000 | 85.9% | 288 MB | 400 | `..._164035.json` |

**结论**：
- **6 个 play 进程是总容量与效率的平衡点**（3599 路，每进程 600 路）
- 8/10 进程时总容量反而下降或每进程效率腰斩（400/进程），系统级开销
  （调度、rtmpstress 客户端、网卡）成为瓶颈，sys CPU 高达 80–99%
- **JIT 对拉流无收益**（3600 vs 3599，噪声级差异）——瓶颈在 socket I/O
- 关 GC 仅略降内存（196→188 MB），对容量无影响——已移除该功能
- 容量从单进程 950 提升到 6 进程 3599（3.8 倍），呈次线性扩展

### 推流容量（1 ingest 进程）

| 配置 | 容量 | 稳态 CPU | 内存 | 每路 | 结果文件 |
|---|---|---|---|---|---|
| 默认 | 800 | 90.5% | 931 MB | 1.16 MB | `capacity_push_..._170351.json` |
| JIT | 800 | **82.4%** | 953 MB | 1.19 MB | `..._170609.json` |

JIT 降低推流路径 CPU 约 9%（FLV 解析被 JIT 编译），建议 ingest 进程开启。
关 GC 版 700 路属判定边界效应（稳态 CPU 78%<80% 阈值，实际仍有余量）。

### 测试期间修复的问题

1. **AsyncTcpConnection 空转**：php_event + Windows 下 async-connect socket 持续触发
   虚假就绪事件，空闲进程烧满 1 核。改为 `fsockopen` 同步建连 + Workerman
   `TcpConnection` 包装（同步建连、异步收发），空闲 CPU 归零
2. **registry 心跳过期误注销流**：`sweepStale` 在高负载/连接重建时把活跃流判死，
   广播 unpublish 导致全部播放端被关闭。已移除 sweepStale 调用——流存活由
   ingest TCP 连接断开（handleClose）即时自愈，无需心跳超时兜底
3. **压测统计基准被瞬时 0 抹掉**：stats 上报有 5s 延迟，`getPlayStreamCount`
   偶发读到 0；脚本改用历史峰值累计，不再把目标路数重置为 0
4. **饱和判定口径**：从"全进程树 CPU 合计 ≥100%"改为"目标角色进程 CPU 平均
   单进程 ≥80% 且持续 30s"，避免多进程时阈值失真

## 场景划分（历史）

| 场景 | 内容 | 脚本 |
|---|---|---|
| **S1** 时延 | 1 路推 + 1 路拉，测帧级转发延迟 | `s1_latency.ps1` |

| 录像 | **关闭**（排除磁盘 IO 干扰） |

### CPU 指标说明

`svc%` 是**服务进程自身**的 CPU（`TotalProcessorTime` 增量 ÷ 墙钟），100% = 用满 1 个核。
`sys%` 是**系统总占用**（24 核归一）。

同时记录两者的原因：测试机上还有其他程序在跑，当 `sys%` 偏高时服务进程可能拿不到足够 CPU，
此时 `svc%` 偏低不代表服务端能力下降。**判断容量看 `svc%`，判断环境干扰看 `sys%`。**

## 结论速览

| 场景 | select | event | 差距 |
|---|---|---|---|
| **S1 时延** | 中位 −6ms | 中位 −14ms | ⚠️ **噪声内，无参考性** |
| **S2 拉流单档** | 200 路 100% 保持 | 500 路 100% 保持 | — |
| **S3 推流单档** | 200 路 100% 保持 | 500 路 100% 保持 | — |
| **S4 拉流加压上限** | **200 路**（300 卡死） | **1000 路**（100% 保持） | **5 倍** |
| **S4 推流加压上限** | **200 路**（300 卡死） | **1200 路**（100% 保持） | **6 倍** |
| **S5 混合 500/500** | — | **98.5% CPU，延迟正常** | — |

**select 的失效方式不是"拒绝连接"，而是整个进程卡死** —— 连 HTTP 管理 API 都不响应。
这是 `FD_SETSIZE=256` 位图溢出的后果，比优雅降级严重得多。

**关于「1000 路是否超载」**：CPU 100% 只是容量边界，真正超载看延迟。
实测 1000 路时新连接首帧延迟从 8ms 暴涨到 1023ms，**确认超载**；
拐点在 900~1000 之间，且接近饱和时延迟剧烈抖动（详见 [S2 的超载判定](#1000-路是超载还是饱和--用延迟判定)）。

> **⚠️ S1 时延数据暂不可用于对比**：测量精度仅 ±30ms（PTS 帧粒度 33ms + `-progress` 粒度 20ms），
> 且出现物理上不可能的负值，说明噪声已覆盖真实值。
> 该数据只能用于检测**数量级**劣化（如 8ms → 1023ms），
> 不能区分「event 比 select 快 8ms」这类细微差异。详见 [S1 说明](#-这组延迟数据暂时没有参考性)。


（`103.0%` vs `100.2%`，见 154907 的两次运行），
12.4 个百分点显著大于噪声，**差异可信**。

按容量推算：相同 CPU 预算下可承载路数约从 **1000 → 1210（+21%）**。

## S1：时延测试

### 方法

推流端与拉流端各自输出「帧 PTS + 当时墙钟」，对同一 PTS 取墙钟差。

关键参数（**容易搞反，加错 PTS 会归零**）：

| 端 | 参数 | 说明 |
|---|---|---|
| 推流 | `-progress <file>`，**不加** `-copyts` | `out_time_us` 才是原始 PTS |
| 拉流 | `-vf showinfo`，**必须加** `-copyts` | `pts_time` 才是原始 PTS |

`-progress` 与 `showinfo` 对 `-copyts` 的反应**相反**。

### 结果

| 事件循环 | 采样数 | 最小 | 中位 | 均值 | P95 | 最大 |
|---|---|---|---|---|---|---|
| event | 10 | −25 ms | **−14 ms** | −6 ms | 26 ms | 26 ms |
| select | 10 | −38 ms | **−6 ms** | −6 ms | 21 ms | 21 ms |

### 解读

**两个循环的时延没有实质差异，都接近 0。**

负值不是错误，是测量噪声：PTS 以帧为粒度（33ms），
`-progress` 以 20ms 为粒度，两者叠加产生 ±30ms 抖动。
真实延迟落在 `[0, 40ms]` 区间，即 **1 帧以内**。

### ⚠️ 这组延迟数据暂时没有参考性

**结论：不要用这组数字做横向对比或容量判断。**

原因：

| 问题 | 影响 |
|---|---|
| **测量精度只有 ±30ms** | 无法区分 10ms 和 40ms，而实际差异可能就在这个量级 |
| **出现负值** | 物理上不可能，说明噪声已覆盖真实值 |
| **PTS 帧粒度 33ms** | 小于 1 帧的差异根本测不出 |
| **`-progress` 粒度 20ms** | 推流端时间戳有 ±10ms 抖动 |
| **两端各自采样** | 采集时刻不同步，引入额外偏差 |
| **口径不同** | 只测「服务器转发」，不含推流编码与播放端解码渲染 |

**这组数据唯一可靠的用途**：检测**数量级**的劣化。

| 场景 | 延迟 | 判断 |
|---|---|---|
| 500 路 | 8 ms | 正常 |
| 1000 路 | **1023 ms** | **明确超载**（128 倍劣化） |

1000 路那次 1023ms 是有效的 —— 它远超噪声范围，是真实的排队现象。
但「event −14ms vs select −6ms」这种差异**在噪声内，不可信**。

**后续若要得到有参考性的延迟数据，需要**：

1. 提高采样同步性（同一进程内同时读两端，而非分两次起 ffmpeg）
2. 用更细的时间源（如 `hrtime()` 直接标记帧到达，而不是解析日志文件）
3. 明确区分「服务器转发延迟」与「端到端延迟」（后者需外部时钟同步）
4. 多次测量取分布，而不是取单次中位数

在此之前，**S1 的数值仅供参考方向，不能作为结论**。

**说明**：这个数值不含推流端编码耗时与播放端解码渲染耗时，
只反映「服务器收到帧 → 转发给拉流端」的耗时。
若要测端到端延迟（含编码与播放缓冲），需另加外部时钟同步。

## S2：拉流并发测试（单档）

1 路推流 + N 路并发拉，每档 40 秒。

**定位**：单点测试，测某一档的绝对表现与稳定性。
**容量判定请看 [S4 逐级加压](#s4逐级加压测试找容量拐点)。**

### select

| 目标 | 实际 | 保持率 | svc CPU | sys CPU | 内存 | 每连接 |
|---|---|---|---|---|---|---|
| 100 | 100 | 100% | 13.4% | 4% | 23 MB | 0.133% |
| 200 | 200 | 100% | 25.1% | 7% | 25 MB | 0.122% |
| **300** | **—** | **0%（卡死）** | — | — | — | — |

**300 路时进程完全卡死**，`getPlayStreamCount` 连续 2 次无响应，脚本提前终止。

### event

| 目标 | 实际 | 保持率 | svc CPU | sys CPU | 内存 | 每连接 |
|---|---|---|---|---|---|---|
| 100 | 100 | 100% | 11.2% | 8% | 24 MB | 0.107% |
| 200 | 200 | 100% | 24.2% | 9% | 26 MB | 0.118% |
| 500 | 500 | 100% | 约 52% | — | 约 30 MB | 0.104% |

> 完整档位数据见 [S4 拉流加压](#拉流加压select-与-event-对照)。

### 单档结论

| 事件循环 | 200 路表现 | 300 路表现 |
|---|---|---|
| `select` | 25.1% CPU，100% 保持 | **卡死** |
| `event` | 24.2% CPU，100% 保持 | 100% 保持 |

**内存不是约束**：1000 连接仅 36 MB（约 36 KB/连接）。

### ⚠️ 1000 路是「超载」还是「饱和」—— 用延迟判定

CPU 到 100% 只说明「单核时间用完了」，是**容量边界**。
是否**超载**要看有没有排队：新连接的首帧延迟是否劣化。

**验证方法**：在 0 / 500 / 1000 路负载下，测同一路新连接的首帧延迟。

| 拉流负载 | svc CPU | 首帧延迟 | 判断 |
|---|---|---|---|
| 0 | 0.6% | −14 ms | 空闲 |
| 500 | 52.6% | **8 ms** | 有余量 |
| **1000** | **99.9%** | **1023 ms** | **已超载** |

**延迟从 8 ms 跳到 1023 ms（128 倍），这是排队的确凿证据。**

进一步细化（每档 5 次采样）：

| 负载 | svc CPU | 首帧延迟 |
|---|---|---|
| 600 | 60.4% | −10 ms |
| 700 | 72.2% | −10 ms |
| 800 | 74.9% | −28 ms |
| 900 | 84.3% | −3 ms |
| 950 | 88.0% | 3 ms |
| **1000** | 96.2% | **24 ms**（另一轮测到 1023 ms） |
| 1050 | 98.8% | −10 ms |

**结论**：

1. **拐点在 900~1000 之间**
2. 接近饱和时**极不稳定** —— 同样的 1000 路，一次测到 24 ms、一次测到 1023 ms
3. 这种抖动本身就是危险信号：生产环境无法接受「时好时坏」

**因此 1000 路不应作为推荐值**，即使它能保持连接。按 50% 设计取 500 是稳妥的。

> 这一节的细化数据（600/700/800/900/950/1050）见
> [S4 加压曲线](#加压曲线event)。

## S4：逐级加压测试（找容量拐点）

**这是判定容量的主要依据。** 从低到高逐档加压，观察：
CPU 增长是否线性、从哪一档开始劣化、事件循环在哪撞墙。

### 为什么必须逐级而不是单点

单点测试看不出拐点：

- 只测 800 路：`select` 直接卡死，看不出「200 是好的、300 是死的」
- 只测 200 路：`event` 只用 24% CPU，看不出上限在哪

| 400 | — | ✅ 100% 保持，50.8% |
| 600 | — | ✅ 100% 保持，72.0% |
| 800 | — | ✅ 100% 保持，82.6% |
| 1000 | — | ✅ 100% 保持，96.1% |
| **1200** | — | ✅ **100% 保持，102.8%** |

**每路约 0.085~0.133% 单核，内存 1.17 MB/路（1200 路需 1.4 GB）。**

### 加压曲线（event）

```
拉流：100 → 11.2%   400 → 43.6%   800 → 85.4%   1000 → 102.0%
推流：100 → 12.7%   400 → 50.8%   800 → 82.6%   1200 → 102.8%
```

**每单位成本随规模下降**（拉流 0.107% → 0.085%，推流 0.133% → 0.085%），
说明固定开销（连接建立、定时器）被摊薄，**仍有小幅余量**。

### 细粒度扫描：找确切拐点

在 600~1050 之间加密采样，每档测 5 次新连接的首帧延迟：

| 负载 | svc CPU | 首帧延迟 |
|---|---|---|
| 600 | 60.4% | −10 ms |
| 700 | 72.2% | −10 ms |
| 800 | 74.9% | −28 ms |
| 900 | 84.3% | −3 ms |
| 950 | 88.0% | 3 ms |
| **1000** | 96.2% | **24 ms**（另一轮测到 **1023 ms**） |
| 1050 | 98.8% | −10 ms |

**观察**：

1. 900 路以内延迟稳定（都在噪声范围内）
2. **1000 路开始抖动** —— 同一负载两次测量差 40 倍
3. 1050 路反而「正常」—— 说明不是线性劣化，而是**在饱和点附近随机排队**

这种不确定性比「稳定劣化」更难处理：**你无法预测下一秒会不会雪崩**。

### 容量推算

| 场景 | 每单位占用 | 单核满载 | **建议（50% 负载）** |
|---|---|---|---|
| 拉流 | 0.10%/连接 | 1000 连接 | **500 连接** |
| 推流 | 0.085%/路 | 1200 路 | **600 路** |

| 推流负载 | 路数 | 内存需求 |
|---|---|---|
| 50%（推荐） | **600 路** | 约 700 MB |
| 80% | 960 路 | 约 1.1 GB |
| 100%（上限） | 1200 路 | 约 1.4 GB |

**内存是推流的真约束**（不像拉流）：约 **1.17 MB/路**。
原因：每路推流要在进程内保留 GOP 缓存（`gopCacheQueue`），
2 秒 GOP × 30fps × 4 Mbps ≈ 1 MB。

## S5：混合推拉测试

**为什么需要**：单测推流或单测拉流都会低估真实负载 —— 生产环境总是同时有推和拉。
而且两者开销结构不同（推流内存密集、拉流连接密集），混跑时的相互影响必须实测。

### 方法

每个用例额外起一路**独立探针流**（`/live/probe`，带 `-progress`），
专门用于在当前负载下测新连接的首帧延迟，不干扰统计。

### 结果（event 循环，每档 45 秒）

| 推流 | 拉流 | svc CPU | sys | 内存 | 推流保持 | 低帧 | 延迟 |
|---|---|---|---|---|---|---|---|
| 50 | 500 | 57.4% | 6% | 95 MB | 50/50 | 0 | −44 ms |
| 100 | 500 | 60.5% | 10% | 158 MB | 100/100 | 0 | −23 ms |
| 200 | 500 | 68.9% | 7% | 288 MB | 200/200 | 0 | −11 ms |
| **500** | **500** | **98.5%** | 15% | 661 MB | 500/500 | 0 | −9 ms |
| 500 | 200 | 73.9% | 12% | 648 MB | 500/500 | 0 | −32 ms |
| 500 | 100 | 61.9% | 15% | 642 MB | 500/500 | 0 | −40 ms |
| 500 | 50 | 61.9% | 11% | 642 MB | 500/500 | 0 | −26 ms |

**全部 100% 保持、零掉帧、延迟都在 1 帧（33ms）以内。**

### 关键发现 1：推流是主要开销

固定拉流 500，推流递增：

```
50/500  → 57.4%
100/500 → 60.5%   (+3.1)
200/500 → 68.9%   (+8.4)
500/500 → 98.5%   (+29.6)
```

固定推流 500，拉流递减：

```
500/500 → 98.5%
500/200 → 73.9%   (-24.6)
500/100 → 61.9%   (-12.0)
500/50  → 61.9%   (0)
```

**拉流从 500 降到 100 释放 36.6% CPU，再降到 50 一点没省** ——
说明拉流的边际成本低（0.10%/连接），推流的单路成本更高。

### 关键发现 2：内存几乎完全由推流决定

```
500/500 → 661 MB
500/200 → 648 MB
500/100 → 642 MB
500/50  → 642 MB
```

拉流从 500 降到 50，内存只掉 19 MB（36 KB × 450 ≈ 16 MB，吻合）。
**推流每路 1.17 MB，是内存的绝对主导项。**

### 关键发现 3：500/500 是「满负荷但未劣化」的临界点

`500/500` 时 CPU 98.5%、延迟仍只有 −9 ms（正常）。
说明能跑到 98.5% 而不出现排队，**但已无 headroom**。

**生产建议（按 50% 设计）**：

| 方案 | 推流 | 拉流 | 预计 CPU |
|---|---|---|---|
| 保守 | 250 | 250 | 约 50% |
| 均衡 | 300 | 200 | 约 55% |
| 推流优先 | 500 | 100 | 约 62% |

## 关键发现

### 1. select 的失效是「卡死」，不是「拒绝」

```
档位 300:
  [ 10s] svc=  40.4% sys=7% ws=26.5MB active=-1/300
  API 连续无响应 → 事件循环卡死，本档终止
```

进程还在（`ws=26.5MB`），但**事件循环停止调度**，连 HTTP 都不响应。
根因：`Select.php` 用 256 位的 fd 位图，超限后 `select()` 返回错误，
Workerman 只打印一行警告就继续跑，实际上已无法处理任何事件。

**这比拒绝连接更危险**：运维看到进程活着，但服务已完全不可用。

### 2. event 的每连接开销比 select 更低

| 场景 | select | event |
|---|---|---|
| 拉流 200 路 | 0.122%/连接 | 0.118%/连接 |
| 推流 200 路 | 0.129%/路 | 0.133%/路 |

拉流场景 event 略优；推流场景几乎相同（推流瓶颈在 GOP 缓存的内存拷贝，不在事件循环）。

**event 的真正优势是「能跑到 1000+」**，而不是「单位成本更低」。

### 3. 拉流内存几乎不随路数增长，推流内存线性增长

| 路数 | 拉流内存 | 推流内存 |
|---|---|---|
| 100 | 24 MB | 151 MB |
| 400 | 28 MB | 540 MB |
| 800 | 35 MB | 963 MB |
| 1000 | 36 MB | 1174 MB |

拉流只需维护连接状态（36 KB/连接）；推流要缓存 GOP（1.17 MB/路）。
**所以推流的内存是规划重点，拉流不是。**

### 4. 逐级加压才能看出拐点

单点测试（比如只测 800 路）看不出：
- select 在 300 就死了（测 800 只会看到"卡死"，不知道 200 是好的）
- event 的 CPU 在 800 之后斜率变缓（0.111% → 0.100% → 0.085%），说明固定开销被摊薄

### 5. 结论：PHP 单进程的真实能力

**event 循环下，1080p30 4Mbps 单进程可撑：**

| 场景 | 单核满载 | 建议（50%） |
|---|---|---|
| 拉流 | 1000 路 | **500 路** |
| 推流 | 1200 路 | **600 路** |
| 混合 | 500 推 + 500 拉（98.5%） | **250 推 + 250 拉** |

这对多进程架构的进程数规划有直接指导意义 ——
按 `总路数 / 单进程建议值` 即可算出需要几个进程。
