# 附录：实测原始数据

全部数据来自本仓库开发环境。

- PHP 8.4.25 (NTS, Win32, VS17, x64)
- Workerman 4.1.9
- Windows
- `shmop` / `sockets` 需显式 `-d extension=` 加载

> **Linux 数据缺失**：开发机无 Linux 环境，POSIX 侧行为均未验证。

## A.1 共享内存扇出

场景：1 个生产进程 → 2 个消费进程，100 KB 帧 × 2000。

```
== 共享内存扇出架构验证 ==
OS=Windows 段大小=6401 KB
槽位=64 帧大小=100 KB 总帧数=2000

推流进程: 2000 帧 / 0.039s (5042 MB/s, 51634 帧/s)

== 消费者结果 ==
  PLAY: 收到=2000 损坏=0 耗时=0.038s 速率=52058 帧/s
  REC:  收到=2000 损坏=0 耗时=0.038s 速率=52000 帧/s

== 判定 ==
  两个消费者均收到全部 2000 帧且无损坏: YES
```

**结论**：一帧可被多进程并发读取，数据完整。

## A.5b 共享内存轮询成本

100 路流，每路一个 16 字节序号槽（合计 1600 字节）。

```
== 共享内存轮询成本实测 ==
OS=Windows PHP=8.4.25
模拟 100 路流，每轮读取全部序号

批量读（一次读 1600 字节）：769.2 万次/秒，单次 0.13 us
单路读（4 字节）：1108.5 万次/秒，单次 0.090 us

== 实际开销推算 ==
  批量读 100 路：0.05 us/次
  单路读：0.038 us/次

  轮询间隔  1 ms：每秒 1000 次，批量读占用 0.051 ms/s（CPU 占比 0.0051%）
  轮询间隔  2 ms：每秒  500 次，批量读占用 0.026 ms/s（CPU 占比 0.0026%）
  轮询间隔  5 ms：每秒  200 次，批量读占用 0.010 ms/s（CPU 占比 0.0010%）
  轮询间隔 10 ms：每秒  100 次，批量读占用 0.005 ms/s（CPU 占比 0.0005%）
```

**结论**：轮询 100 路序号（间隔 2ms）CPU 占用 **0.0026%**，
远优于 socket 通知（3000 帧/s × 0.025ms = 75 ms/s）。

**这是采用轮询作为消费者同步机制的决定性依据。**

## A.6 Windows 端口复用不分流

两个进程绑同一端口（`so_reuseport`），均 `bind=OK`，发送 20 个连接后：

```
进程A: accepted by 39552 × 20
进程B: （无输出）
```

**结论**：Windows 上不能依赖端口复用做多进程分流。

## A.10 单线程事件循环的跨流拖累

模拟 3 路流，每路 100 轮；场景 2 中只有 A 每次 `usleep(20ms)`。

```
--- 场景 1：三路都快 ---
  A: 0.000 s
  B: 0.000 s
  C: 0.000 s

--- 场景 2：只有 A 慢（每次 20ms）---
  A: 3.077 s
  B: 3.057 s
  C: 3.057 s

B 被 A 拖慢 30566 倍（0.000s → 3.057s）
C 被 A 拖慢 30566 倍（0.000s → 3.057s）
```

**结论**：单线程事件循环中，任何一路的耗时都会**串行累加到全局**。

**推论**：

1. 录像必须独立成进程（否则慢盘拖慢推流与播放）
2. **录像也必须多进程**（否则一个慢盘拖慢所有流的录像）
3. 背压必须收敛到单路流（不能因为一路慢就阻塞所有推流）

这是"录像池要多进程"的决定性依据。

| 端 | 参数 | 说明 |
|---|---|---|
| 推流 | `-progress <file>`，**不加** `-copyts` | `out_time_us` 才是原始 PTS |
| 拉流 | `-vf showinfo`，**必须加** `-copyts` | `pts_time` 才是原始 PTS |

### 关键发现 1：`select` 的失效方式是「卡死」

```
档位 200: svc=25.1%  active=200/200    ✅
档位 300: svc=40.4%  active=-1/300     ❌ getPlayStreamCount 连续无响应
```

进程还活着（`ws=26.5MB`），但**事件循环停止调度**，连 HTTP API 都不响应。
根因：`Select.php:117` 用 256 位 fd 位图，超限后只打印警告继续跑，实际已无法处理事件。

**这比拒绝连接危险**：运维看到进程活着，但服务完全不可用。

### 关键发现 2：`event` 能跑到 1000+ 路

装 `event` 3.2.0（libevent 绑定）后，拉流 1000 路、推流 1200 路全部 100% 保持，
单核占用刚过 100%。

**注意不能用 `ev`**：`ev`（libev）在 Windows 上能加载、定时器正常，
但**监视 socket 时报 `Libev error(10038)` = `WSAENOTSOCK`**。
PHP stream 的 `(int)$stream` 是内部 fd 编号，不是 WinSock `SOCKET` 句柄；
`event` 自带 `EventUtil::getSocketFd()` 做转换，所以能用。

### 关键发现 3：内存约束在推流侧

| 路数 | 拉流内存 | 推流内存 |
|---|---|---|
| 100 | 24 MB | 151 MB |
| 400 | 28 MB | 540 MB |
| 800 | 35 MB | 963 MB |
| 1000 | 36 MB | 1174 MB |

拉流只需连接状态（36 KB/连接）；推流要缓存 GOP（1.17 MB/路）。
**所以推流的内存是部署规划重点。**

### 关键发现 4：逐级加压才能看出拐点

单点测试看不出边界。只测 800 路时，`select` 直接卡死，
看不出「200 是好的、300 是死的」这条线。

event 的每路占用也随路数下降（0.111% → 0.100% → 0.085%），
说明固定开销被摊薄，说明还有余量。

### 推算：单核满载容量

| 场景 | 每单位占用 | 单核满载 | **建议（50% 负载）** |
|---|---|---|---|
| 拉流 | 0.10%/连接 | 1000 连接 | **500 连接** |
| 推流 | 0.085%/路 | 1200 路 | **600 路** |

**这些数字的前提**：单进程只用 1 个核（事件循环单线程）。
实际部署必须留 headroom（突发、GC、日志），建议按 50% 设计。

**Windows 上必须换 `Event` 事件循环**，否则 200 路以上就卡死，CPU 远未用满。
