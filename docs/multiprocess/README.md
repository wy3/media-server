## 结论速览

**Linux：三个进程池 + 控制进程，用 `SO_REUSEPORT` 横向扩展。**
**Windows：单进程降级。** 两者共用同一套 `FrameBus` 抽象，代码不分叉。

| 维度 | 决策 |
|---|---|
| 推流池 | 端口 **1935**，`reuseport`，N 个进程 |
| 播放池 | 端口 **18080**，`reuseport`，M 个进程 |
| 录像池 | 无端口，**K 个进程（按 path 哈希分片）** |
| 控制进程 | 端口 **18081**，单实例 |
| 帧如何跨进程 | 共享内存环形缓冲，**消费者由 UDP 组播 + EV_READ 唤醒** |
| 录像丢帧 | **不丢帧**（背压 + 5s 超时兜底） |
| 播放丢帧 | 允许（低延迟优先） |
| 跨机器扩展 | 不支持 |
| 单推流进程容量 | **1080p30 约 415 路 / 4K30 约 215 路**（单核 50% 负载） |
| 单进程容量（1080p30 4Mbps） | **拉流 1000 路 / 推流 1200 路**（单核满载） |
| 建议负载（50%） | **拉流 500 / 推流 600** |
| Windows 连接上限 | **默认 253 后卡死**；装 `event` 可到 1000+ |

## 为什么录像池也要多进程

单线程事件循环下，**一路慢会拖慢全部**。实测：

```
场景 1：三路都快  → A: 0.000s  B: 0.000s  C: 0.000s
场景 2：只有 A 慢  → A: 3.077s  B: 3.057s  C: 3.057s
```

即使 B/C 自身耗时为 0，也必须等待 A 的慢 IO 完成。

因此录像**必须**：

1. 独立成进程（不与推流/播放同进程）
2. **按 path 哈希分片到多个录像进程**（否则一个慢盘拖慢所有流）
3. 背压收敛到单路流（不能一路慢就阻塞全部推流）

## 为什么必须分成推流池和播放池

`SO_REUSEPORT` 让内核**随机**分配连接。若推流和播放混在一个池里，
播放请求可能落到没有该路流的进程上。

因此用**两个不同端口**做隔离——内核按端口分别做负载均衡。

## 核心简化：确定性 key

播放进程**不需要查询**流在哪：

```php
$key = shmKeyForPath($path);   // crc32 推导，所有进程一致
$shm = shmop_open($key, 'w', 0, 0);
```

| 旧设计 | 本设计 |
|---|---|
| Gateway 维护路由表 | **无路由表** |
| 播放端查询 `path → worker` | **直接 attach** |
| 需要 `query_route` 消息 | **不需要** |

## 核心收益

**只有一件事值得为多进程付出复杂度：录像写盘不再阻塞事件循环。**

当前单进程下，录像 `fwrite` 落盘阻塞整个事件循环，直接表现为播放卡顿。
拆出录像池后这个阻塞被隔离。

## 容量速查（单进程，仅用 1 核，1080p30 4096kb/s）

**拉流（1 路推 + N 路拉）**：

| 负载 | 连接数 | 内存 |
|---|---|---|
| 50% | **500** | 30 MB |
| 80% | 800 | 35 MB |
| 100%（实测上限） | **1000** | 36 MB |

**推流（N 路并发推，不拉流）**：

| 负载 | 路数 | 内存 |
|---|---|---|
| 50% | **600** | 700 MB |
| 80% | 960 | 1.1 GB |
| 100%（实测上限） | **1200** | 1.4 GB |

**内存差异的原因**：拉流只需连接状态（36 KB/连接）；
推流要缓存每路 GOP（约 1.17 MB/路，2s GOP × 30fps × 4Mbps）。
**推流的内存是规划重点。**

**时延**：帧级转发延迟约 **0~40ms**（1 帧以内），select 与 event 无实质差异。

### 事件循环对比（同一机器实测）

| 场景 | `select`（默认） | `event`（libevent） |
|---|---|---|
| 拉流上限 | **200 路** | **1000 路** |
| 推流上限 | **200 路** | **1200 路** |
| 失效方式 | **300 路时进程卡死**（连 HTTP API 都不响应） | 无 |
| 时延 | 中位 −6 ms | 中位 −14 ms |

**`select` 在 253 连接后不是拒绝新连接，而是整个事件循环停摆** ——
进程还活着但完全不响应，比优雅降级更危险。

> `ev`（libev）在 Windows 上**不可用** —— 监视 socket 报 `WSAENOTSOCK`，
> 因为 PHP stream 的 fd 不是 WinSock `SOCKET` 句柄。
> 必须用 `event`（自带 `EventUtil::getSocketFd()` 转换）。
